## En une phrase

L'architecture de la vue est bonne : moteur isolé derrière un import dynamique, rendu à la demande testé sans navigateur, couche accessible réelle, commandes du plan tout ou rien avec contrôle de version. Mais **en production, le canvas ne s'affiche jamais** : la CSP bloque l'`eval` dont PixiJS a besoin, et la suite e2e accepte ce repli sans broncher.

## Ce qui est bien fait

- **PixiJS confiné** :
  - un seul point d'entrée, `src/game/GardenCanvas.tsx`, chargé par `next/dynamic(..., { ssr: false })` (`src/game/GardenView.tsx:20`) ;
  - MAP-01 le prouve en e2e, avec un contrôle positif : la signature `__PIXI_APP_INIT__` est absente des scripts de la vue classique et présente dans ceux de la vue jardin (`tests/e2e/scene.spec.ts:16`).
- **Rendu à la demande testable** : `RenderLoop` (`src/game/engine/loop.ts`) reçoit un renderer et un ordonnanceur injectés. MAP-08 et la limite à 30 i/s sont vérifiés en unitaire, sans WebGL (`tests/unit/scene.test.ts`).
- **Commandes du plan tout ou rien** :
  - `applyPlanCommands` verrouille la ligne du jardin (`for('update')`), compare `plan_version`, puis applique le lot dans un point de sauvegarde (`src/features/scene/plan.ts:23-31`) ;
  - les commandes de zone repassent par les services de zone : permissions, restrictions de zone, RG-ZON-05, événements ;
  - PLN-03, PLN-04 et PLN-08 sont prouvés sur une base réelle (`tests/integration/scene.test.ts`).
- **Couche accessible réelle, pas décorative** : un bouton par entité, avec `aria-label`, `data-state` et focus visible. A11Y-03 parcourt toute la scène au Tab, vérifie le contour de focus, ouvre la feuille avec Entrée et rend le focus à la fermeture (`tests/e2e/scene.spec.ts:36`).
- **Règles pures et bornées** : `visualPhase`, le filtre ambiant, la grille et le repli des frames sont des fonctions pures testées (MAP-05 à 07, MAP-11, PLN-07). L'instantané est validé par Zod avant de partir au client (`src/features/scene/snapshot.ts:60`).

## Constats majeurs

### M1 — En production, la CSP bloque PixiJS : la vue jardin n'affiche jamais le canvas
**Fichiers** :
- `src/server/security-headers.ts:5` ;
- `src/game/engine/pixi-scene.ts:1` ;
- `tests/e2e/scene.spec.ts:12`.

```ts
`script-src 'self' 'nonce-${nonce}' 'strict-dynamic'${isDev ? " 'unsafe-eval'" : ''}`,
// pixi-scene.ts
import { Application, Assets, Container, ... } from 'pixi.js';
```

**Problème** : PixiJS v8 génère la synchronisation des uniforms avec `new Function` (`node_modules/pixi.js/lib/rendering/renderers/gl/shader/utils/generateUniformsSync.js`). Il faut donc `'unsafe-eval'`, ou l'import `pixi.js/unsafe-eval`, qui fournit des versions précompilées. En dev, la CSP autorise `eval` ; en production, non.

**Constat** :
- build de production lancé (`next build` dans `.next-audit`, puis `next start`) ;
- la vue jardin des Tilleuls passe à `data-canvas="unavailable"` ;
- la page reçoit deux violations `CSP script-src eval`.

La vue se rabat silencieusement sur le rendu de repli en CSS.

**Conséquence** : la fonctionnalité centrale du lot est invisible pour tout utilisateur en production. La suite e2e ne peut pas le voir : `sceneReady` accepte `ready` **ou** `unavailable`, y compris en CI, où les e2e tournent pourtant sur `next build` puis `next start`.

**Correction** :
- importer `pixi.js/unsafe-eval` dans `pixi-scene.ts`, plutôt que d'ouvrir `'unsafe-eval'` dans la CSP ;
- n'accepter `unavailable` en e2e que si le contexte n'a vraiment pas de WebGL : vérifier `WebGLRenderingContext`, ou exiger `ready` sous Chromium.

**Effort** : S
**État** : ✅ corrigé — `a899247` (import `pixi.js/unsafe-eval` ; vérifié sur `next build` + `next start` : rouge sans, vert avec) et `cd39455` (`sceneReady` exige `ready`)

### M2 — Chaque reconstruction de la scène fuit des objets PixiJS
**Fichier** : `src/game/engine/pixi-scene.ts:97`, `:109`, `:123`, `:146-147`

```ts
ground.removeChildren();
// ...
zoneLayer.removeChildren();
```

**Problème** : `removeChildren()` détache les enfants sans les détruire. Chaque `setSnapshot` recrée tous les `Graphics`, `TilingSprite` et `Sprite`, alors que les anciens gardent leurs géométries GPU. `setSnapshot` est appelé à chaque revalidation dans la vue, et à **chaque geste** dans l'éditeur (`src/game/PlanEditor.tsx`, abonnement à l'historique).

**Conséquence** : la mémoire GPU et JS croît linéairement au fil d'une session d'édition : quelques centaines d'objets par geste dans un jardin de 40 zones. Sur mobile, cela mène à une perte de contexte WebGL.

**Correction** : `removeChildren().forEach((c) => c.destroy())` (les textures de l'atlas sont partagées : ne pas passer `texture: true`). Mieux encore, réutiliser les nœuds par identifiant d'entité, ce qui préparera le précalcul par blocs du §9.1.

**Effort** : S
**État** : ✅ corrigé — `e96dd3c` (5 occurrences ; pas de test automatisé, WebGL requis)

### M3 — L'éditeur peut lancer deux enregistrements sur la même version de plan
**Fichier** : `src/game/PlanEditor.tsx:104-127`

```ts
const save = async () => {
  ...
  if (!h.done.length || status === 'saving') return;
// ...
saveTimer.current = window.setTimeout(() => void save(), AUTOSAVE_MS);
```

**Problème** : `status` est l'état React lu dans la fermeture où `schedule` a été appelée. Un geste fait pendant un enregistrement en cours programme un enregistrement automatique qui voit encore `status !== 'saving'`. Il part avec la même `baseVersion` et renvoie **toutes** les commandes non réinitialisées, y compris celles déjà envoyées.

**Conséquence** : si le premier enregistrement dure plus de 1,5 s, le second reçoit `CONFLICT`. Le rejeu rapporte alors à tort « 1 modification n'a pas pu être rejouée » : la zone déjà créée se chevauche elle-même. L'utilisateur croit avoir perdu un geste. Selon l'ordre des réponses, l'historique local peut aussi être réinitialisé sur une base périmée.

**Correction** : un `useRef` « enregistrement en cours » lu au moment de l'exécution. Envoyer seulement les commandes non encore envoyées, et réenregistrer à la fin si de nouveaux gestes sont arrivés.

**Effort** : S
**État** : ✅ corrigé — `d81eed6` (e2e avec enregistrement ralenti, rouge avant la correction)

### M4 — Sur mobile, les cultures sont des cibles de 8 px
**Fichiers** :
- `src/game/viewport.tsx:19` et `:26` ;
- `src/game/GardenView.module.scss:92` ;
- `src/game/GardenView.tsx:130`.

```ts
return Math.min(4, Math.max(0.25, Math.floor(z * step) / step));
// .culture { width: 32px; height: 32px; }   — dans le monde, mis à l'échelle par la caméra
```

**Problème** : le recadrage initial fait tenir toute la scène dans la largeur. À 390 px, un jardin de 16 m donne un zoom de 0,25. Les boutons de culture, dimensionnés en pixels du monde, font alors **8 × 8 px** à l'écran.

**Conséquence** : sur l'appareil cible (§9.5 : toucher, pincer), les cultures sont quasi impossibles à toucher avant de zoomer, bien sous les 24 px du critère 2.5.8 des WCAG 2.2 et des 48 px de `--touch-min`. MAP-03 passe parce que Playwright clique au centre exact du bouton, ce qu'un doigt ne fait pas.

**Correction** :
- dimensionner les boutons de culture en pixels d'écran : contre-échelle `1/zoom` ou couche positionnée hors transformation ;
- ou plafonner le dézoom initial sur mobile, et ouvrir sur la zone la plus active plutôt que sur toute la scène.

**Effort** : M
**État** : ✅ corrigé — `533fe84` (cultures ; les zones très petites restent proportionnelles à leur surface)

### M5 — Les géométries des commandes du plan ne sont pas bornées
**Fichiers** :
- `src/features/scene/snapshot.schema.ts:7` ;
- `src/features/scene/plan.schema.ts:19-23` ;
- `src/features/scene/plan.ts:63` et `:75`.

```ts
export const rectSchema = z.object({ v: z.literal(1), kind: z.literal('rect'), x: z.number().int(), y: z.number().int(), w: z.number().int().positive(), ... });
```

**Problème** : le schéma partagé de l'instantané sert aussi à valider les **entrées** de `plan.apply`. Il accepte des coordonnées négatives et sans maximum, alors que le schéma des zones les borne (`src/features/zone/schema.ts:8` : `min(0).max(1_000_000)`). `createZone` repasse par `zoneCreateSchema` et reste protégé. En revanche, `resizeZone` et `moveZone` (`setZoneGeometry`) et `addTerrain` écrivent la géométrie telle quelle.

**Conséquence** :
- déplacer une zone racine au-delà du bord gauche de la grille enregistre `x < 0` : la zone sort de `sceneBounds`, qui ne calcule que des maxima, et devient inatteignable sur le plan ;
- une commande forgée peut écrire des coordonnées énormes, ce qui fait exploser `bounds` et la taille de la grille dessinée (`drawGrid`, une ligne par tuile).

**Correction** : un schéma d'entrée borné pour les commandes (réutiliser `rectGeometrySchema`), distinct du schéma de sortie.

**Effort** : S
**État** : ✅ corrigé — `53ac8fa` (schéma d'entrée borné et gestes de l'éditeur bornés)

## Constats mineurs

- **Dépendance inversée** : `src/features/scene/snapshot.ts:15` importe `familyKey` depuis `@/game/manifest`. Une feature serveur dépend du dossier du moteur client ; c'est sans effet aujourd'hui, mais fragile.
- **Taille de composant** : `src/game/PlanEditor.tsx` fait 346 lignes : gestes, enregistrement, rejeu, formulaire et barre d'outils dans un seul composant. Les gestes et l'enregistrement mériteraient un hook chacun.
- **Double-tap** : sur une zone, il recentre (`GardenView.tsx`, `onDoubleClick`) au lieu de zoomer, contrairement au §9.5.
- **`plan.apply` sans plafond de débit** : jusqu'à 200 commandes par appel, chacune passant par un service avec ses requêtes (`plan.schema.ts:34`). Les autres contenus ont `CONTENT_LIMITS`.
- **Recherche quadratique** : `out.find` dans la boucle de placement des cultures (`snapshot.ts:113`). C'est borné à 1 000 cultures, donc négligeable aujourd'hui.
- **Géométrie sans contrainte en base** : `zone.geometry` et `terrain_element.geometry` sont du `jsonb` sans `CHECK` sur la forme (`kind = 'rect'`, `w > 0`). La validation n'est faite que par Zod.
- **Commentaires `eslint-disable-line react-hooks/exhaustive-deps`** : cinq occurrences dans `GardenView.tsx` et `PlanEditor.tsx`, pour des stores créés une seule fois. Un `useState(() => create…())` l'exprimerait sans désactiver la règle.
- **Mineurs des audits précédents toujours ouverts** : ceux listés au lot 6, notamment :
  - classement sur l'XP de toujours ;
  - écriture pendant le GET des quêtes ;
  - titres de quêtes non traduits ;
  - `pnpm audit` : 1 vulnérabilité modérée (outillage).
